# Архитектура проекта

## Границы модулей

- `bot.py` — discord.py events, обработка сообщений, задачи и lifecycle; `commands/` — разделённые slash-команды.
- `registration.py`, `ui/` — формы и карточки; интерфейс не владеет игровыми правилами.
- `ai/` — протокол провайдера, адаптер OpenAI-compatible API, промпт и валидируемая схема.
- `judge.py` — сбор ограниченного актуального контекста и создание записи вердикта.
- `game_engine.py` — allowlist показателей, валидация и атомарное применение/отмена дельт.
- `models.py`, `database.py`, `migrations/` — сохраняемое состояние и миграции.
- `security.py` — проверка привязки к одному Discord Guild.

## Поток игрового поста

1. Проверяются сервер, владелец государства, приватный канал (для треда используется parent channel),
   уникальный Discord message ID. Повтор неуспешной обработки атомарно захватывается блокировкой строки,
   поэтому параллельные delivery одного исходного поста не запускают AI дважды.
2. Сохраняется исходный пост, проставляется реакция ожидания.
3. В ИИ передаются пост, эпоха/правила сервера, экономика, склад, действующая промышленность,
   военные показатели, технологии, лор с лексическим подбором, сводка и последние исторические события.
   Пост явно помечен недоверенными игровыми данными.
4. Pydantic проверяет JSON; игра игнорирует свободные неизвестные ключи через запрет extra.
5. Лимит проверяется по локальной дате; дополнительные публикации хранятся в выдаваемых грантах.
6. В автоматическом режиме игровой движок применяет только известные и допустимые дельты внутри
   транзакции. В режиме модерации изменения остаются предложенными до подтверждения.
7. Payload Reply встраивается в `VerdictOutbox` атомарно с вердиктом; отправитель lease-claim'ит запись,
   отвечает через `message.reply(...)`, затем сохраняет Discord ID. После сбоя lease истекает, а перед
   повторной отправкой сверяется история ответов. Reply всегда остаётся в исходном канале/Thread.

## Данные

`GuildConfig`, `Country`, `EconomicStats`, `ResourceDefinition`, `CountryResource`, `ResourceProduction`,
`Epoch`, `CountryLore`, `GamePost`, `Verdict`, `VerdictOutbox`, `StatChange`, `PostLimitGrant`, `TradeOffer`, `DailyRun`,
`IndustryFacility`, `ConstructionProject`, `ResearchProject`, `CountryTechnology`, `MilitaryStats`, `HistoricalEvent`,
`LoreSummary`, `ResourceOperation`, `EconomicOperation` и `AuditLog` хранят конфигурацию сервера, игровой мир,
баланс и историю изменений. Сделки
переводят деньги/ресурсы лишь при подтверждении получателем и в одной транзакции. Уникальный ID сообщения
и идемпотентные `DailyRun` защищают от повтора; PostgreSQL использует `SELECT FOR UPDATE`. В SQLite
блокировки строк не эмулируются, поэтому SQLite не подходит для многопользовательской эксплуатации.

## Технические решения и ограничения текущего этапа

- SQLAlchemy async; PostgreSQL — production, SQLite — локальные тесты.
- AI адаптер отделён от движка. Другие провайдеры реализуют `AIProvider.judge`.
- У ИИ нет доступа к базе/Discord; только прикладной слой валидирует и коммитит изменения.
- При штатном завершении бот отменяет фоновые циклы и освобождает пул SQLAlchemy.
- Начальная миграция строит таблицы из SQLAlchemy metadata; последующие изменения схемы должны
  добавляться отдельными ревизиями.
- Добыча ресурсов конфигурируется `/resource-add`, `/resource-adjust`, `/resource-disable`,
  `/resource-enable` и `/production-set`; `/industry-set` настраивает
  автоматические циклы предприятий с проверкой входных ресурсов и эксплуатационных расходов.
  `/military-set`, `/technology-set`, `/epoch-set`, `/lore-add`, `/economy-adjust`, `/post-grant` доступны
  администраторам. Ресурсные и денежные операции сохраняют значения до/после.
- Ежедневная экономика сериализует расчёт блокировкой статистики и повторно проверяет `DailyRun` после
  получения блокировки. Ресурсные и заводские циклы коммитятся по одному определению с row locks;
  сбой одного цикла не отменяет остальные и не останавливает периодический worker.
- Ежедневная экономика запускается идемпотентно по локальной дате и отправляет отчёт в канал государства.
- Торговые предложения `/trade-offer` → `/trade-accept` или `/trade-decline`; списание проверяется при
  принятии, а перевод денег/ресурсов выполняется атомарно. Для разных валют применяется только настроенный
  администратором направленный курс `/exchange-rate-set`.
- AI может предложить строительный проект с резервированием казны/ресурсов; он завершается за несколько
  успешных ходов и создаёт предприятие. Упрощённое исследование не требует стоимости и предпосылок: у страны
  может быть один проект на 1–5 успешных ходов, после которого открывается следующий уровень технологии.
  Отмена завершённых проектов/исследований и полное дерево технологических эффектов пока не реализованы.
- Поиск контекста лора использует лексическое совпадение словоформ; сводка важных событий автоматически
  компактизируется пакетами по десять событий, а администратор может заменить её и править записи через
  `/lore-edit`, `/lore-delete`, `/lore-summary-set`, `/event-add`, `/history-search`. Это extractive timeline,
  не семантическое резюме моделью. Reply outbox повторяет доставку с backoff и сверкой недавней истории;
  абсолютное exactly-once между PostgreSQL и Discord невозможно без общей транзакции. Встроенное
  расписание бэкапов и live-интеграционные испытания ещё не настроены.
